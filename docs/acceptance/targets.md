# Targets

How a chart reaches each of Aioros's targets: the web through Aioros's slot writers (per request, without Avalonia),
the desktop through Avalonia's drawing context.

| Id | Criterion |
|---|---|
| WEB-01 | Given a chart spec recorded as JSON and an app's records (not dictionaries), when `ChartRenderer.Create` builds the renderer once and it writes the bound records through a slot output, then it reads each data key through the member lookup Aioros gives it (the app's generated accessors) and writes the same markup as `ChartSvg.Write` does for the same values. |
| WEB-02 | Given a chart control laid out at 500 × 300, when Aioros asks it how it is written (`IWrittenBySlot.WrittenSlot`), then it names `ChartRenderer`, the `Data` property as the bound value, and an argument whose spec writes the same markup as Recharts' render of the example. |
| DESKTOP-01 | Given SimpleBarChart built from its XAML elements, when the desktop control draws it (Avalonia, Skia, Inter at 14 px, device scale 1), then the frame keeps the screenshot's size and fewer of its inked pixels than the example's limit (ORACLE-03) differ by more than 64 in a channel from Recharts' screenshot in Chromium. |
| DESKTOP-02 | Given DetailsFollowLineChart (SimpleLineChart with a tooltip) in a window, when the pointer rests at (150, 40) over the second category, then the chart's hovered category is 1 and its frame, against the frame before, draws Recharts' cursor line down the category (x 145, where Recharts' recorded cursor `M145,5L145,248` stands; more than 80% of its blank pixels painted `#ccc`, the active dots over it), each series' active dot at Recharts' recorded center in its fill (`#8884d8`, `#82ca9d`), the tooltip box's `#ccc` left border at Recharts' recorded box position (155, 50) and more than 300 pixels of text inside it (its label and two lines); when the pointer leaves the plot, then no category is hovered and the frame is the frame before the hover, pixel for pixel |
| DESKTOP-03 | Given a chart bound to an observable collection, when an item is added, then the chart lays itself out again: the data holds the new item and the y domain grows to cover it. |
| DESKTOP-04 | Given a chart declared in XAML whose line's `Stroke` is bound to the model, when the model's color changes, then the desktop chart lays itself out again and its spec and its line take the new color (child elements follow their bindings through the chart's data context). |
| WEB-04 | Given the writer of a compiled page's chart, when it writes the same items three times, then every write produces `ChartSvg.Write`'s bytes and only the first two lay the chart out (the second keeps its markup, the third writes it again); when a value, then (after the new values were written twice and kept) only a category text changes, or an item is added, then the writer lays the chart out again and writes the new markup, never the kept one. |
| WEB-05 | Given a chart that fills its parent with `ResponsiveWidths` 360, 720 and 1080, when it is written, then the markup holds three charts laid out at 360, 720 and 1080 px (each with its own view box and its own visible ticks), each taken away by container queries outside its range of 0–540, 540–900 and 900 px and up (AUDIT-46), inside one `pictor-responsive` container; the same chart without widths, or with a fixed width, is written once. |
| WEB-06 | Given a chart whose line's `Stroke` is bound to the model, when Aioros asks the chart how it is written, then the slot declares the line's `Stroke` as a part read under its own key and the argument records the spec with a hole at the line's stroke; the renderer writes the line in the color the plan reads for that key (`#ff0000`, then `#00ff00` on the next request), byte for byte as the chart written from a spec holding that color, and two requests with the same color build the spec once. |
| WEB-07 | Given a pie whose own `Data` is bound and a chart whose `Title` is bound, when the renderer writes them with the values the plan reads, then the pie's sectors are the bound list's (read into the table of the keys the pie reads), a list changed in place between two requests gives the new sectors, and the wrapper's label is the bound title. |
| WEB-08 | Given a bar chart whose bar's `Fill` is a `LinearGradientBrush` with a gradient stop whose `Color` is bound (a value the spec does not copy: the stop renames its gradient), when Aioros asks the chart how it is written, then no part is declared for it, so Aioros's plan still refuses the page with the property's name rather than writing it frozen; a bound property the spec does not change with (the desktop's `ReduceMotion`) is declared with no hole. |
| WEB-09 | Given two charts on one page that fill their parents with different `ResponsiveWidths` (380 and 760, then 380 and 620), when they are written one after the other, then each rule that takes a layout away names the wrapper and its range (`.pictor-responsive>.recharts-wrapper.pictor-w570-up`) and no rule names every wrapper, so the later chart's rules never take away the earlier chart's layout at its width. |
| WEB-10 | Given the writer of a compiled page's chart whose series run a click command, over 300 categories whose markup exceeds 85 KB (the large object heap's threshold), when it writes new values on every request, then each write allocates less than the markup's size (what is left is the layout's and the click targets' small objects; it allocated 2.6 times the markup's size when the render grew its own array): the chart is laid out into a buffer rented from the shared array pool and returned once the markup and its commands are copied to the output, so no array grows with the markup and none reaches the large object heap; a kept markup is the only copy made, once a data version is seen twice. Precedent: Aioros's pooled body buffers (SSR-91); Kestrel and System.Text.Json write through `ArrayPool<byte>.Shared`. |
| WEB-11 | Given a chart that fills its parent's width at an aspect ratio (`Aspect` 16/9, `ResponsiveWidths` 542, its spec 300 px tall) and one that fills its parent, when they are written, then the first is laid out at 542 × 304.875 px (the width over its ratio, as its wrapper's `aspect-ratio` sizes it, not its spec's height) and each surface is a block (`style="width:100%;height:100%;display:block"`, as Recharts 3's surface), so an inline surface's line box adds nothing under it and the wrapper is as tall as its `aspect-ratio` makes it (304.83 px at 542 px, not 4 px more). |
