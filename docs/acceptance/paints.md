# Paints: gradients and brushes

Recharts fills and strokes series with any SVG paint, gradients included: an example declares a `linearGradient` in the
chart's `defs` and names it `url(#id)`. In XAML the natural equivalent is an Avalonia brush on the series' `Fill` and
`Stroke`: a `LinearGradientBrush` is written on the web as a `linearGradient` in the chart's `defs` and drawn natively
on the desktop, a solid brush as its color, and a color text as Recharts takes it.

| Id | Criterion |
|---|---|
| PAINT-01 | Given Recharts' AreaChart with two `linearGradient` fills in its `defs` (`colorUv` and `colorPv`, from 0.8 to 0 opacity down the area, `fillOpacity` 1), when Pictor writes it, then its markup matches Recharts' render, each area's fill naming a gradient with the same line and stops, and the surface opens with a `defs` holding both gradients with their ids, lines and stops (`offset="5%"`, `stop-color`, `stop-opacity`). |
| PAINT-02 | Given the same chart written in XAML with a `LinearGradientBrush` (start 0,0 and end 0,1 relative, its stops' alphas as the stops' opacities) as each area's `Fill`, when its spec is built, then the markup matches Recharts' render; the spec names each gradient by its content (`pictor-gradient-` and a hash), so the same brush on two series defines one gradient and different brushes never share an id; a `SolidColorBrush` is written as its color (`#82ca9d`, or `#82ca9d80` when translucent) and a color text as it is. |
| PAINT-03 | Given that chart on the desktop, when it is drawn, then its pixels match Recharts' render in Chromium within the tolerance of the other examples (fewer than 4% of inked pixels differ strongly), the areas fading down as in Recharts. |
| PAINT-04 | Given a chart with a gradient fill laid out at several widths (`ResponsiveWidths`), when it is written, then each layout defines its own copy of the gradient named with the layout's class (`pictor-gradient-…-pictor-w0-540`) and its paints name that copy, since a gradient defined inside a hidden layout paints nothing in the browser; a chart at one width keeps the gradient's own id. |
| PAINT-05 | Given a line with `StrokeWidth="0"`, a point whose neighbours are null, and `DotRadius="4"` with `DotFill="red"`, when it is written, then every defined point is drawn with a circle of radius 4 filled red and stroke width 0, isolated points included, as Recharts draws `dot={{r: 4, fill: 'red'}}` with `strokeWidth={0}`; without `DotFill` the dot keeps the line's default white fill, as Recharts' does, so a mark with no line names its fill. |
| PAINT-06 | Given SimpleBarChart whose `Bar` has `FillKey="color"` and `OpacityKey="dim"`, its items carrying those members (the second `#ff0000` and 0.4; the others none), and a `Cell` on the third item with a `#00ff00` fill, when the data is bound and the chart is written, then the second bar is filled `#ff0000` with opacity 0.4, an item without the members keeps the series' fill and no opacity, and the cell wins over its item, as Recharts spreads an item's `fill` over its bar and a `Cell`'s props over both; a chart whose data changes between requests shows the change. Found in a real app, whose selected month could not stand out. Precedent: Recharts' data items with a `fill`, the form shadcn/ui's charts use. |
| PAINT-07 | Given a `Scatter`, a `Pie`, a `RadialBar` and a `Funnel` with `FillKey="color"` and `OpacityKey="dim"` whose first item carries `#ff0000` and 0.4 and whose second carries neither, when each chart is written, then the first shape is filled `#ff0000` with opacity 0.4 and the second has neither, as Recharts 2.15.4 spreads an item's `fill` and `opacity` onto those shapes (checked with Recharts); a `Line`'s and an `Area`'s dots take no such key, as Recharts builds them from the series' props and never reads the item's `fill` (checked with Recharts). |
